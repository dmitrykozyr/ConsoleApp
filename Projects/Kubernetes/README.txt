Kubernetes — система оркестрации контейнеров. Она автоматически:
- запускает Docker-контейнеры на нескольких машинах
- перезапускает упавшие контейнеры
- масштабирует приложение (больше/меньше копий)
- балансирует трафик между копиями
- обновляет версии без простоя (rolling update)

	┌─────────────────────────────────────────────────────────┐
	│                    Kubernetes Cluster                    │
	│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
	│  │   Node 1    │  │   Node 2    │  │   Node 3    │     │
	│  │ ┌─────────┐ │  │ ┌─────────┐ │  │ ┌─────────┐ │     │
	│  │ │  Pod    │ │  │ │  Pod    │ │  │ │  Pod    │ │     │
	│  │ │(.NET app)│ │  │ │(.NET app)│ │  │ │(.NET app)│ │     │
	│  │ └─────────┘ │  │ └─────────┘ │  │ └─────────┘ │     │
	│  └─────────────┘  └─────────────┘  └─────────────┘     │
	│         ▲                                                │
	│         │ Service (балансировщик)                        │
	│         │ Ingress (внешний доступ)                       │
	└─────────────────────────────────────────────────────────┘

	Объект				| Что делает
	--------------------------------------------------------------------------
	Pod					| Минимальная единица — один или несколько контейнеров
	Deployment			| Управляет Pod'ами: сколько копий, как обновлять
	Service				| Стабильный сетевой адрес для доступа к Pod'ам
	Ingress				| HTTP-маршрутизация снаружи кластера
	ConfigMap / Secret	| Конфигурация и секреты
	Namespace			| Логическое разделение ресурсов

	Файлы конфигурации:
	├── deployment.yaml     # Как запускать приложение
	├── service.yaml        # Как к нему обращаться
	└── configmap.yaml      # Внешняя конфигурация

В Dockerfile описано:
- взять среду для сборки .NET
- скомпилировать программу
- взять облегченную среду для запуска
- положить туда скомпилированную программу
- сказать: «программа слушает порт 8080»

Схема портов:

	Ваш curl → localhost:30080  (nodePort)
				  ↓
			 Service :80       (port)
				  ↓
			 Pod :8080         (targetPort / containerPort)
				  ↓
			 Ваша программа

Команды для терминала Docker:

	Перейти в проект
		cd C:\Repos\ConsoleApp\Projects\Kubernetes\Kubernetes_
	Команда сборки
		docker build -t k8s-demo-app:1.0 .
	Проверка
		docker images k8s-demo-app
	Убедиться, что кластер работает
		kubectl config get-contexts
		kubectl get nodes
	Кластер не видит локальный образ из docker images - нужно загрузить
		kind load docker-image k8s-demo-app:1.0 --name desktop
	Применить настройки Kubernetes
	Kubernetes прочитает все три файла *.yml и создаст объекты
		kubectl apply -f k8s/
	Проверить, что копии запустились
		kubectl get pods
	Открыть доступ к приложению. Пока окно открыто — приложение доступно
		kubectl port-forward svc/k8s-demo-app-service 30080:80

Команды для другого терминала PowerShell:
При обращении к адресам ниже Kubernetes сам решит, какие поды обработаю запрос,
в зависимости от их загруженности и доступности

	Запрос 1 — главная страница
		curl http://localhost:30080/
	Запрос 2 — балансировка (выполнить 5–10 раз подряд, должно менять хост)
		curl http://localhost:30080/
	Проверка здоровья
		curl http://localhost:30080/health
	API с данными
		curl http://localhost:30080/api/items

	Посмотреть сервисы
		kubectl get svc
	Посмотреть логи
		kubectl logs -l app=k8s-demo-app
	Увеличить число копий до 5
		kubectl scale deployment k8s-demo-app --replicas=5
	Перезапустить все копии
		kubectl rollout restart deployment k8s-demo-app
	Удалить под, после этого будет создан новый
		kubectl delete pod k8s-demo-app-56494c888-z8t27


	В Kubernetes есть 3 вида проб, чтобы следить за здоровьем программ

		Startup Probe (Проба запуска)
			- программа запустилась?
			- при провале ждет, пока эта проба не пройдет успешно, тем временем остальные проверки не начинаются
			- нужна, т.к. некоторые программы долго просыпаются при старте
			  и без этой првоерки Kubernetes подумал бы, что программа зависла, и начал бы её бесконечно перезапускать
			- реализуется через HealthChecks с разными тегами на разные эндпоинты
		
		Liveness Probe (Проба живучести)
			- программа еще жива или окончательно зависла?
			- при провале перезапускает контейнер
			- проверяет только внутреннее состояние приложения (крутится ли главный поток)
			  Нельзя включать сюда проверку БД - если БД упадет, и сто приложений начнут проверять её через Liveness,
			  Kubernetes решит, что сломались сами приложения и начнет одновременно перезапускать все сто контейнеров,
			  создав лавину перезапусков (веерный перезапуск)
			- реализуется через адрес '/health/live', который говорит 'я принимаю запросы'
		
		Readiness Probe (Проба готовности)
			- спрашивает, готова-ли программа обрабатывать их запросы?
			- при провале временно отключает подачу трафика на этот контейнер, контейнер не перезапускается
			- бывает, программа работает, но прямо сейчас занята: прогревает кэш, или на секунду потеряла связь с БД
			  В этот момент отправлять туда клиентов нельзя — они увидят ошибку
			  Kubernetes временно прячет этот контейнер от пользователей, а когда связь восстановится, включает обратно
			- реализуется через адрес '/health/ready', который говорит 'я принимаю запросы и есть связь с БД'
