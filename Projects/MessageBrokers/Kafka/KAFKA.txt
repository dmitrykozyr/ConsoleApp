- сообщение сохраняется на диске от нескольких дней до бесконечности, его можно перечитать заново
- потребители сами приходят в Kafka и вытягивают данные, когда готовы их обработать, что позволяет потребителям работать в своем темпе
- создана для Big Data - может переваривать миллионы сообщений в секунду, распределяя их по множеству серверов (кластеру)

	Загрузить и запустить Docker-контейнер для Kafka
	docker run -d --name kafka -p 9092:9092 apache/kafka:latest
	Сначала запустить проект Kafka.Producer
	Отправить REST запрос из папки RestClient, после чего сообщение будет добавлено в очередь
	Запустить проект Kafka.Consumer, после чего он вычитает сообщение из очереди

Брокер сообщений, используется в микросервисах для пересылки сообщений между сервисами

При использовании Kafka микросервисная архитектура становися похожей на Enterprise Service Bus,
когда сервисы не здают друг об друге, а центральный узел знает

Сообщения поступают от Producer к Consumer
Один Producer может отправлять сообщения одному | нескольким Consumer

Producer_1 -> |       | -> Consumer_1
Producer_2 -> | Kafka | -> Consumer_2
Producer_3 -> |       | -> Consumer_3

Kafka Cluster объединяет несколько брокеров для репликации данных

Zookeeper - оркестратор нескольких брокеров,
в котором хранится конфигурация и состояние кластера

У брокера есть топик, а у топика партиции, в которых хранятся сообщения
        
В каждом брокере должны храниться реплики(копии) партиций из других брокеров
        
У каждой партиции могут быть копии и одна главная Leader-партиция,
только в нее пишутся данные и из нее читаются, в остальные происходит реплицирование
        
Если Leader недоступен, Zookeeper назначает другого Leader из списка реплик
    
Некоторые реплики могут хранить неактуальные данные, поэтому некоторые реплики помечены как ISR,
в них репликация идет в первую очередь и из них выбирается новый Leader
        
Не должно быть такого, что все Leader находятся на одном брокере - на него будет сильная нагрузка,
нужно распределить по разным брокерам

|----------------------------------------------|
            | Broker_1 | Topic A | Partition_0 |
            |          |         |             |
            |----------|-----------------------|
    Zookeeper  | Broker_2 | Topic A | Partition_1 |
            |          |         | Partition_2 | В этом брокере 2 партиции, а в следующем 0 - несбалансированность
            |----------|-----------------------|
            | Broker_3 | Topic A | Partition_0 | Репликация партиции из первого брокера для надежности
            |          |         |             |
|----------------------------------------------|

Структура отправляемого через Kafka сообщения:
- Key
- Value
- Time
- Headers

Какие гарантии доставки бывают и что реально достижимо?
    - At-most-once — коммитим оффсет до обработки, теряем сообщения при падении
    - At-least-once — коммитим после обработки, получаем дубли - это рабочий дефолт
    - Exactly-once - транзакции продюсера плюс read_committed на консьюмере дают атомарность связки «прочитал — обработал — записал в топик»
      Как только в обработке появляется внешний побочный эффект — запись в БД, вызов чужого API — сквозного exactly-once нет
      Поэтому at-least-once на транспорте плюс идемпотентность на приёме, что даёт effectively-once с точки зрения бизнеса

Как устроено партиционирование и что с порядком сообщений?
    Порядок гарантируется только внутри партиции
    Поэтому ключ партиционирования выбирается по сущности, для которой порядок важен
    — идентификатор заказа
    - клиента
    - счёта
    Все события одной сущности попадают в одну партицию и обрабатываются последовательно
    Число партиций задаёт потолок параллелизма консьюмеров: больше консьюмеров в группе, чем партиций, лишние простаивают
    Увеличивать число партиций на живом топике можно, но это ломает существующее распределение ключей, поэтому запас закладывается заранее
    Осторожно с «горячими» ключами: один крупный клиент способен перекосить нагрузку на одну партицию

Consumer groups, ребалансировка, лаг — что важно на проде?
    Группа делит партиции между инстансами
    При добавлении, падении или таймауте участника происходит ребалансировка, во время которой обработка встаёт
    Отсюда практические вещи:
    - разумные session.timeout и max.poll.interval, чтобы долгая обработка не выглядела как смерть консьюмера;
    - cooperative sticky assignment вместо eager, чтобы не останавливать всю группу;
    - тяжёлую работу выносить из цикла poll
    Consumer lag — ключевая метрика здоровья: он должен быть на дашборде и под алертом, потому что растущий лаг означает
    что мы не успеваем за продюсером, задолго до того, как это заметит бизнес

Что такое transactional outbox и зачем он?
    Запись в БД и отправка в брокер — два разных ресурса, и атомарно их не связать:
    упали между ними — либо потеряли событие, либо отправили событие о том, чего в базе нет
    Outbox решает это так: в одной локальной транзакции с бизнес-данными пишем строку в таблицу outbox,
    а отдельный процесс (поллер или CDC через Debezium) читает её и публикует в Kafka, помечая отправленное
    Транзакция одна, поэтому расхождения быть не может; публикация становится at-least-once, что закрывается идемпотентностью потребителя
    Обратная сторона — задержка публикации и необходимость чистить таблицу

Как делаете консьюмера идемпотентным?
    Каждое сообщение несёт устойчивый бизнес-ключ или message id
    На стороне потребителя ведётся таблица обработанных ключей, и вставка идёт с уникальным индексом: повторная обработка падает на конфликте и молча пропускается
    Второй приём — делать саму операцию идемпотентной по природе: upsert вместо insert, установка состояния вместо инкремента, проверка текущего статуса перед переходом
    Дедупликация должна жить в той же транзакции, что и бизнес-эффект, иначе она бесполезна
    Дополнительно — версия или timestamp события, чтобы отбрасывать устаревшие сообщения при повторной доставке

Retention, компакция, replay — как используете?
    Retention по времени или размеру — для потоков событий;
    log compaction — когда топик хранит последнее состояние по ключу и используется как источник для восстановления
    Replay — сильная сторона Kafka: можно поднять новый сервис и переиграть историю с нужного оффсета, чтобы наполнить его проекцию
    Но replay безопасен только если потребители идемпотентны и побочные эффекты контролируемы — иначе переигрывание разошлёт клиентам повторные уведомления
    Поэтому на проде это отдельная процедура с отключением внешних эффектов
